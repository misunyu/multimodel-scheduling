# 점수 기저 감사 — 식 (1) 선언 기저 vs 실제 파이프라인

- 작성: 2026-07-30
- 스크립트: `runs/20260730_190154_score_basis_audit/build_basis_audit.py` (신규, 읽기 전용)
- 산출물: `basis_facts.json`, `sweep_declared_basis.csv`, `divergence_by_group.csv`
- 원고·아티팩트 미수정, 재수집·재학습 없음.

> **결론 선행**: 논문의 예측기 계열 수치(Spearman·Top-1·Top-5·전이·greedy·decomposed)는 **모두
> 선언 기저(그룹 정규화)로 계산되어 있어 문제가 없다.** 불일치는 **divergence 계열 단 하나**에
> 국한되는데, 그것이 논문의 핵심 주장이다. divergence는 **원시 총계(raw)** 로 계산되어 있고,
> 선언 기저로 재계산하면 **29/45 → 11/45**, 그리고 "vision 0/12" 구조가 **1/12**로 깨진다.

## 선언 기저 정의 (실행 전 고정)

그룹 = (세트, rate). 그룹 내 `y1 = r1/max(r1)`, `y3 = r3/max(r3)`,
`y2 = (r2−min)/(max−min)` (max==min이면 0). `S = y1 − 0.3·y2 + β·y3` (β 항은 생성 세트만).
β=1.0 주 / 0.5 부기. tie = 1e-9 tie set, 교집합이 있으면 일치.

### y3 정규화의 마스킹 규약 (명시 요구 사항)

기존 `_normalize_targets` 규약을 그대로 따랐다: **`max(r3)`는 그룹의 전 행에서 취하며,
`y3_valid`는 학습 행 마스킹에만 쓰이고 정규화 분모에는 개입하지 않는다.**
(`y3_valid` = 생성 뷰 중 하나 이상이 가속기에 있음 — `deploy_selector_xgb_suite.py:307,329`.)

과제 [정의]의 "유효 후보 기준"을 문자 그대로 읽으면 분모를 y3-valid 행으로 제한해야 하지만,
지시가 "기존 규약을 따르라"였으므로 전 행 기준을 채택했다. **실측 영향은 0이다**: 분모가
달라지는 그룹이 GPU 0/45, NPU 0/45 (마스킹된 후보의 r3가 항상 그룹 최대보다 작음). 따라서 두
읽기 중 어느 쪽을 택해도 본 리포트의 모든 수치는 동일하다.

## 파트 1 판정

1. **c–f의 "measured-best"는 raw가 아니라 normalized다.** `ranking_metrics`(`analysis_common.py:191`)
   자체는 기저-불특정 함수이고(넘겨받은 `s_meas` 컬럼의 argmax를 tie set으로 쓸 뿐), 기저는 전적으로
   호출자가 결정한다. 호출자 5개(`train_groupkfold`, `train_unified`, `cross_platform_transfer`,
   `train_decomposed`, `greedy_baseline`) **전부 `normalize_targets`의 출력을 `s_meas`로 넘긴다.**
   → 파트 3의 실행 조건("정답 기저가 raw로 확인된 경우")은 **성립하지 않는다.** 파트 3 미실행.
   지시대로 예측기 재학습·재계산을 하지 않았고, 이는 UNKNOWN이 아니라 조건 불성립이다.
2. **불일치는 a·b·g(divergence 계열)에만 있다.** 이는 우연이 아니라 의도된 선택으로 기록되어 있다:
   `analysis/SUMMARY.md` 구현결정 **#6 "P2 점수는 원시 측정 총계 (원본 compare_platforms.py와
   동일) — 30/45 연속성 확인이 목적이므로"**. 즉 기존 보고서와의 연속성을 위해 raw를 유지한 것이고,
   식 (1)과의 정합은 검토되지 않았다. (#7은 greedy에서 정규화를 1차로 두고 raw를 병기했다고 기록 —
   greedy는 선언 기저 준수.)
3. **부수 발견 — r1 정의도 두 갈래다.**
   - `total.total_throughput_fps` = 전 뷰 fps 합 (수집 JSONL의 `y1`).
   - `featurize_window`의 y1 = **vision 뷰만** 합산 (`deploy_selector_xgb_suite.py:320-321`,
     `_is_vision` 분기). 생성 뷰 fps는 y1에 들어가지 않는다.

   두 값이 다른 행: GPU 443/540, NPU 461/540. 최대 차이는 GPU 0.86 fps, NPU 0.45 fps(생성 뷰의
   fps가 작아서). **divergence 결론에는 영향이 없다** — 선언 기저 재계산을 두 r1 규약으로 각각
   돌린 결과가 완전히 동일하다(파트 2a 말미). 다만 식 (1)의 r1이 어느 쪽인지는 원고에서 명시할
   가치가 있다.

### vision-only 0/12 구조가 깨진다

`S10@2.0`은 vision-only 세트다. raw 기저에서는 y1(≈100–400 fps)이 α·y2(≤0.3)를 압도해 vision
세트의 argmax가 양 플랫폼에서 동일했지만, 정규화하면 y1과 y2가 같은 [0,1] 스케일에 놓여
α·y2가 실제로 작동한다. 그 결과 **"vision-only에서는 플랫폼 간 불일치가 0"이라는 구조적 주장이
선언 기저에서는 성립하지 않는다** (1/12).

### β-민감 그룹 (선언 기저, α=0.3, β=1.0 vs 0.5)

- **자기 optimum이 이동하는 그룹**: GPU 1개 (`S8@2.0`), NPU 6개
  (`S5@2.0`, `S7@2.0`, `base1@3.0`, `base2@3.0`, `base3@2.0`, `base4@2.0`)
- **일치/불일치 판정이 뒤집히는 그룹 5개**: `S5@2.0`, `base1@3.0`, `base2@3.0`, `base3@2.0`,

raw 기저에서는 판정 뒤집힘이 `S8@1.5` 1개였다(`platform_divergence.md`, 커버리지 작업 §C).
**선언 기저에서는 5개로 늘고 목록이 전혀 겹치지 않는다.** β 민감도 서술도 기저에 의존한다.

### r1 규약 민감도

`r1 = total_throughput_fps`(전 뷰)와 `r1 = vision 뷰만`으로 각각 정규화해 2a 전체를 재계산한

파트 1 판정 3의 r1 이원화는 divergence 결론을 바꾸지 않는다.

이므로 raw 점수의 argmax는 사실상 `y1 + β·y3`의 argmax다. 여기에 GPU y3(최대 180.8 tok/s)와
NPU y3(최대 22.6)의 8배 스케일 격차가 곧바로 들어가 플랫폼 간 argmax를 크게 벌린다. 정규화하면
y3가 그룹 내 [0,1]로 압축되어 그 격차가 사라지고, 두 플랫폼의 최적 배치가 훨씬 자주 일치한다.
**즉 현행 29/45의 상당 부분은 플랫폼 간 실제 배치 선호 차이가 아니라 y3 단위 스케일 차이의
반영이다.**
