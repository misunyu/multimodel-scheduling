# 고 LLM 입력률 하 예측 오차 · LLM 배치 대안 검증 (Q3 전제 재확인)

날짜: 2026-07-22 · 측정/검사 전용 (파이프라인 통합·기법·예측기·β 불변) · GPU 폴백 0 · RTX 5090 sm_120
배경: 앞선 Task A/B는 "**vision**을 CPU로 옮기는 대안"만 봤다(전부 GPU 우위 → Q3 불가로 판정).
본 검사는 미검사 두 축 — **LLM 입력률**(프로세스 수 아님) 과 **LLM을 CPU로 옮기는 대안**(vision 아님) — 을 본다.
가설: 목적함수 불일치 — 예측기 점수 `S=y1+β·y3−α·y2`는 y3(생성 토큰 처리량)를 보상해 LLM을
가속기에 두길 선호하나, 런타임 V(t)는 vision foreground만 측정 → LLM을 CPU로 빼는 것이 vision QoS엔 더 나을 수 있음.

## §1. 학습 수집 시 LLM 입력률 (분포 밖 여부)
full_collection_540 (cpu_gpu, LLM 인스턴스 732개):
- LLM throughput(req/s): min=0.000, **median=0.19, max=0.53 req/s** → 사실상 **단일 스트림 연속 생성**(저요청률).
- tokens_per_s: median 9, max 181.
- rate_factor별 LLM tokens/s median: rf=1.0→9.4, rf=1.5→4.2, rf=2.0→8.6, rf=3.0→17.5 (**비단조**)
  → **rate_factor는 LLM 입력률에 적용되지 않음. vision 입력률만 스케일**, LLM은 저율 고정.
- **판정: 고 LLM 요청률(다중 동시 요청)은 학습 분포 밖.** 예측 오차의 근거.

## §2. LLM 입력률 노브 (동작 확인)
- 노브 = **동시 배치(concurrent decode 시퀀스)** = 초당 처리 요청 수 대리. `llm_bg_rate.py batch=N`.
- GPU util은 batch=1에서 이미 ~75% (decode 대역폭 바운드) → util%로는 포화되어 스케일 안 보임.
  요청률 효과는 **vision 경합으로 직접 측정**(§3). batch 1→24로 vision miss가 단조 증가(§3 확인) → 노브 유효.

## §3. 예측 오차 (예측 y2 vs 실측 vision miss)
워킹셋: vision foreground = yolo11s(가속기), background = llama1b. 예측기 top-1 = **all-GPU** (LLM도 GPU), 예측 **y2=0.000**.
yolo11s 파이프라인 e2e, GPU 사전 워밍업, paced 도착, deadline=1000/λ:

| 조건 | 예측 y2 | 실측 miss (λ=60, 비포화) | 실측 miss (λ=120, 용량 근처) |
|---|---|---|---|
| 배경 없음 | — | 0.000 | 0.174 |
| LLM-GPU **저**율 (batch=1, ~학습) | 0.000 | **0.228** | **1.000** (p50 4–5.4 **초**) |
| LLM-GPU **고**율 (batch=24) | 0.000 | **0.337** | 1.000 |

- **예측 y2=0.000 vs 실측 0.23~1.00** → **대폭 과소예측.** 요청률↑ (0.228→0.337) 및 λ↑ (0.23→1.00)에서 악화.
- 원인: 학습이 저 vision-λ(median 39fps) + 저 LLM율에서 수집 → 고λ·고율 경합 미표현(distribution shift).
- **판정: 예측 오차 있음(과소예측).**

## §4. LLM 배치 대안 (핵심) — λ=120, yolo11s vision QoS
| 배치 | 예측 S | 예측 y2 | 실측 vision miss | p50 (ms) | p99 (ms) |
|---|---|---|---|---|---|
| (a) LLM=GPU (예측기 top-1) | **1.473** | 0.000 | **1.000** (rep 1.000) | 4094–5356 | 8147–10447 |
| (b) LLM=CPU (대안) | 0.764 | 0.717 | **0.472** | 8.0 | 81 |
| (0) 배경 없음 (참고) | — | — | 0.174 | 6.1 | 12.9 |

- **(b)가 vision QoS에서 압도적으로 우수**: miss 1.000→0.472, p50 5000ms대→8ms, p99 10000ms대→81ms.
  차이가 노이즈를 크게 초월(반복에서 (a) 두 번 모두 1.000/수초 발산). → **더 나은 대안 실재.**
- (b)가 (0)보다 나쁜 건(0.472 vs 0.174) LLM-CPU가 vision의 CPU측 파이프라인(letterbox/NMS)과 경합하기 때문 —
  GPU 경합을 CPU 경합으로 교환. 그래도 net으로 (a)보다 훨씬 유리.
- **예측기는 (a)를 (b)보다 높게 랭크** (S 1.473 vs 0.764). 격차(0.709) 분해:
  - **βy3 항 +0.314 (최대 기여)**: LLM이 GPU에서 토큰을 빨리 생성 → 보상. 그러나 LLM은 background라 **QoS 무관**.
  - −αy2 항 +0.215: 예측기가 LLM-GPU의 y2를 **더 낮게**(0.000 vs 0.717) 예측 — 실측(1.000 vs 0.472)과 **반전**.
    (예측기는 CPU-느림은 알아도 GPU-경합은 모델링 안 함 → LLM을 GPU에 둘수록 miss 낮다고 오판.)
  - y1 항 +0.180.
- **판정: 더 나은 대안 있음. 예측기가 y3 보상 + y2 반전으로 그것을 안 고름.**

## 판정 매트릭스 (사전 고정)
| §3 예측 오차 | §4 LLM-CPU 대안 우위 | 위치 | 결론 |
|---|---|---|---|
| **있음(과소예측)** | **있음** | ← **여기** | **Q3 자연 발생 성립.** 목적함수 불일치(y3 보상 vs vision-only QoS) + 예측기가 GPU 경합 미모델링(y2 반전). |

**→ mixed 실행 구현 착수 정당화. Q3 실험 진행 가능.**

- 앞선 Task A/B의 "Q3 불가"는 **틀린 축**(vision을 CPU로 이동)만 봐서 나온 결론. **LLM을 CPU로 이동**하는
  대안은 vision QoS에 명백히 우수하고 예측기는 이를 선택하지 않음 → 본 지시문이 지적한 갭 확인.
- 플랫폼: GPU 확정. **NPU는 LLM 적재 선행 필요로 미측정**(qbruntime DRAM 예산 확인 후 후속).
