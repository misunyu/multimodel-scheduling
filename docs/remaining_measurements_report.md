## 0. 한 줄 요약

**NPU가 GPU보다 위험하지 않다 — 오히려 훨씬 안전하다.** 전환 중 NPU DRAM 증분은 최대 **+26 MiB**
(16384의 0.16 %, 여유 **557배**)로, GPU VRAM의 +574 MiB(32607의 1.8 %, 여유 49배)보다 **한 자릿수
작다.** 사전 우려("디바이스가 절반이니 비중이 두 배")는 성립하지 않았고, 이유는 명확하다 —
NPU의 vision 모델은 사전 컴파일된 `.mxq`라 3종 합쳐 **52 MiB**다. **호스트 RSS는 두 플랫폼이 같은
자릿수**(+3291 vs +3099 MiB, 여유 17배 vs 18배)이며, 전환 비용의 지배항은 디바이스가 아니라
**생성 모델 가중치의 호스트 적재**다. YOLO11x 단독 지속 처리율은 **61.5 ± 5.3 fps**(Q4의 λ=90은
1.46배). churn 누적은 n=8에서도 **분리되지 않았다.**

## 1. 작업 206 — NPU 전환 피크 (**최우선**)

### 1.1 NPU DRAM을 읽을 수 있는가 — **읽을 수 있다**

`mblt-status -q -s MEMORY,PROCESS_INFO`가 nvidia-smi에 해당한다: 장치 사용량(/16384 MB)과
**PID별 귀속량**을 낸다. `scripts/mem_sampler.py --npu`가 이를 파싱해 `mem.csv`에 세 열을 더한다.

> **파서를 한 번 틀렸고 그것이 관측으로 드러났다.** 첫 파일럿에서 `npu_ours`가 0인데 `npu_total_used`가
> 1918 MiB였다. 프로세스 표가 행 단위가 아니라 **여러 줄**이기 때문이다 —
> `Process ID : N` 다음에 들여쓴 `NPU : X MB`가 따라온다. 행 단위 정규식은 조용히 아무것도 귀속시키지
> 못했다. 상태 기반 파서로 고쳤고, 계측이 틀린 채로 얻은 파일럿 2런은 **삭제**했다(커밋 전, 참조 없음).

### 1.2 조건 — λ는 지시문의 25/45가 아니라 **25/80**이다

지시문과 v32 확정표 v2의 Q5 행은 λ=25/45로 적는다. **실제로 돈 것은 25/80이다**:
`generate_schedules.py`가 `q5_misprediction`을 `(…, 25, 80)`으로 정의하고, 커밋된 스케줄과 v33 Q5
런 20개의 `schedule_snapshot.yaml`이 전부 burst 80이며 스냅샷과 현재 스케줄 파일은 **바이트 동일**하다.

논문의 Q5 값은 전부 그 조건에서 나왔으므로 **80으로 돌았다.** 45로 재면 어떤 게재값에도 대응하지 않는
구성을 재는 것이 된다. **확정표 v2의 Q5 λ 표기는 오기다**(§4에 판단 항목으로 올린다).

### 1.3 배경 기동 — 6런 전수 확인 (판정 전에)

```
[bg-llm llama1b/npu] loaded (4332 ms); generating continuously
[bg-llm] start llama1b on npu (pid 87123); waiting for load
[bg-llm llama1b/cpu] loaded (2795 ms); generating continuously
```

NPU에 LLaMA-1B가 적재되고 생성하며, 회복 배치에서 CPU로 이전한다. `mblt-status`가 그 순간을 독립적으로
확인한다 — 실행기 프로세스 **52 MB**(vision 3종) + `bg_entry` 자식 **1866 MB**(LLM) = 1918 MB.

### 1.4 자원 표 — **GPU와 나란히**

정의는 v38과 동일(정상 상태 = 창 앞뒤 2 s 중앙값, 증분 = 피크 − 인접 정상 상태의 큰 쪽).

| 플랫폼 | 전환 종류 | n | 지표 | 증분 평균 | **증분 최대** | 피크 유지 | 피크 | **여유** |
|---|---|---|---|---|---|---|---|---|
| **CPU–NPU** | 생성 이전 | 11 | host RSS | +1099 | **+3291** | 0.76 s | 10688 MiB | **17×** |
| | | 11 | **NPU DRAM** | +3.1 | **+26** | 1.98 s | 1922 MiB | **557×** |
| | vision in-place | 2 | host RSS | +21 | +37 | 0.90 s | 5047 MiB | 1600× |
| | | 2 | **NPU DRAM** | −2.0 | **0** | 0.90 s | 1914 MiB | 오버슈트 없음 |
| **CPU–GPU** (v38) | 생성 이전 | 6 | host RSS | +1988 | +3099 | 0.10 s | 10514 MiB | 18× |
| | | 6 | GPU VRAM | −1110 | **0** | 1.23 s | 4896 MiB | 오버슈트 없음 |
| | vision in-place | 16 | host RSS | +171 | +649 | 1.71 s | 8206 MiB | 94× |
| | | 16 | **GPU VRAM** | −98 | **+574** | 1.61 s | 5628 MiB | 49× |

가용량: 호스트 RAM 63562 MiB / GPU VRAM 32607 MiB / **NPU DRAM 16384 MiB**.

### 1.5 읽는 법 — 사전 우려가 반대로 나왔다

v38은 *"GPU에서 +574 MiB가 나온 이상 16 GB 디바이스에서 0이라고 가정할 근거가 없다"*고 적었다.
맞는 경계였으나, 실측은 **NPU 쪽이 한 자릿수 안전**하다.

- **NPU DRAM 증분은 12전환 중 9건이 정확히 0**, 나머지가 +4 / +4 / +26 MiB다. 최대 +26 MiB =
  16384의 **0.16 %**.
- 이유는 하드웨어 여유가 아니라 **모델 표현**이다. NPU는 사전 컴파일된 `.mxq`를 적재하므로 vision
  3종이 **52 MiB**다. GPU는 뷰마다 ORT/CUDA 세션이 붙어 정상 상태가 4.8–5.5 GiB이고, vision swap에서
  두 세션이 겹치는 순간이 +574 MiB를 만든다.
- **정상 상태 점유도 NPU가 낮다**: 1922 MiB(11.7 %) 대 GPU 5628 MiB(17.3 %). LLM이 CPU로 빠지면
  NPU는 52 MiB만 남는다.

**즉 이 시스템에서 전환의 디바이스 메모리 위험은 NPU 쪽이 아니라 GPU 쪽이 크다.**

### 1.6 그러나 호스트 RSS는 두 플랫폼이 같다

생성 모델 이전의 host RSS 증분은 NPU +3291 / GPU +3099 MiB, 여유 17배 / 18배로 사실상 같다.
당연한 결과다 — 그 전환의 비용은 **LLM 가중치를 호스트 RAM에 적재하는 것**이고, 그 일은 가속기가
무엇이든 동일하다. **전환 비용의 지배항은 디바이스가 아니다.**

### 1.7 표본의 한계

`vision` 행이 **n=2**다. Q5는 cand_2에서 회복하므로 순수 vision 전환이 드물게 일어난다.
GPU의 n=16과 비교할 수 없고, "NPU vision swap은 오버슈트가 없다"는 **이 두 전환에서 그렇다**는
뜻이다. 생성 이전은 n=11로 충분하다.

## 2. 작업 207 — 논문이 잃은 두 수치

### 2.1 vision-4 비교(5.2 대 3.4) — **실행하지 않았다. λ를 되찾을 수 없다**

논문 §IV-A의 문장은 *"Measured at a load high enough to induce violation"*을 전제한다.
문서에 남은 유일한 vision-4 λ는 **52**이고, `docs/hotswap_buffer_bias_fix.md` §6c가 그 조건을
이렇게 기록한다:

> 네 기법 모두 **위반에 진입조차 하지 않는다** … 이 워크로드는 λ=52에서 그냥 **feasible**하다.

따라서 5.2/3.4를 낳은 λ는 52가 아니고, **그 값은 저장소 어디에도 없다.**

- λ=52로 돌면 위반이 없어 비교가 성립하지 않는다(그 사실은 이미 기록돼 있다).
- 위반이 나는 λ를 **골라서** 돌면 §0.4가 금지하는 "결과에 맞춰 λ를 고르는" 일이 된다.

**그러므로 실행하지 않았다.** 실행하려면 λ를 **새로 정하는 결정**이 먼저 있어야 하고, 그것은 계측이
아니라 판단이다(§4). 사유는 `docs/v39_conditions.md`에 실행 전에 적혀 있다.

### 2.2 YOLO11x 단독 처리율 — **61.5 ± 5.3 fps**

`schedules/probe_yolo11x_gpu.yaml`(생성기가 만든 단일 모델 포화 프로브, λ=400 fps/뷰, buffer 300),
3반복. **완료 프레임 수**(`perframe.csv`)를 초당으로 세고 워밍업 5 s를 버렸다.

| 런 | 창 | 지속 처리율 |
|---|---|---|
| r0 | 38 s | 69.0 ± 1.0 fps |
| r1 | 39 s | 58.5 ± 0.9 fps |
| r2 | 38 s | 57.1 ± 0.9 fps |
| **평균** | | **61.5 ± 5.3 fps** |

- **런간 산포가 8.6 %로 크다**(r0가 나머지보다 빠르다). 런 내부 산포는 ±1 fps로 작으므로 런 간
  요인(열, 첫 실행 캐시)으로 보이나 **확인하지 않았다.** 그래서 sd를 함께 싣는다.
- **Table~I의 13.07 ms(=76.5 fps)와 혼동하면 안 된다.** 그것은 격리 추론 지연이고, v35가 보였듯
  파이프라인이 지탱하는 값이 아니다. 논문 문장이 말하는 *"what the accelerator sustains"*는 후자다.
- **Q4의 λ=90은 이 값의 1.46배**다. 논문의 주장(*"well above what the accelerator sustains"*)은
  성립한다. 제거됐던 게재값 ≈72 fps는 측정 범위(57–69)보다 위이며 격리값 76.5에 더 가깝다.

## 5. 작업 210 — 등재·주석

### 5.1 확정표

**신규 19항목, 갱신 2항목**(494 → 513). 전 항목 `source`가 런 디렉터리를 가리킨다.

| 그룹 | id |
|---|---|
| NPU 생성 이전 | `hs_npu_gen_{rss,dram}_{incr,incr_max,hold,headroom}` (8) |
| NPU vision swap | `hs_npu_vision_{rss,dram}_{incr,incr_max,hold}` + `_rss_headroom` (7) |
| NPU 피크·용량 | `hs_npu_peak_{rss,dram}`, `hs_npu_dram_total` (3) |
| 프로브 | `q4_yolo11x_sustained` = 61.5 ± 5.3 fps (1) |
| **갱신** | `hs_{bg,a}_final_rss` — n=3 → **n=8** |

**갱신을 택한 이유**: 같은 양을 더 나은 표본으로 다시 잰 것이지 새 양이 아니다. 둘 다 남기면 한 사실에
두 수가 생기고, 그것이 v37이 한 라운드를 들여 청소한 실패 양식이다. 옛 값은 각 항목의 `note`에 적었다.

어휘는 v38의 `rss`·`vram`·`hold`·`headroom`을 재사용했다. `vram`은 v39부터 **가속기 메모리 일반**
(GPU VRAM과 NPU DRAM)을 뜻하며, 어느 디바이스인지는 id(`hs_npu_*`)와 `note`가 밝힌다.
검사기 주석에 그 확장을 적었다.

### 5.2 주석 목록 — **줄 번호를 버리고 앵커로 바꿨다**

이번 라운드에 §III 문단이 추가되면서 **뒤의 18개 대상이 전부 한 줄씩 밀렸다.** 그런데
`gen_cv_worklist.py`는 현재 `main.tex`에서 해시를 다시 뽑으므로 **밀린 자리의 해시가 그대로
"일치"했다** — 즉 sha256 가드가 이 경우를 잡지 못한다. 실제로 잘못된 줄에 붙어 47건이 불일치로
터진 뒤에야 드러났다.

**고쳤다**: 목록 항목이 이제 줄 번호가 아니라 **문장의 고유 부분 문자열(anchor)** 을 담고,
생성 시 정확히 한 줄로 해석되지 않으면 실패한다. 해시는 그대로 두어 "정본이 그 사이 바뀐" 경우를
계속 잡는다.

### 5.4 **검사기가 잡은 것 — §III의 3.1 GiB가 확정표와 다르다**

논문 §III(L365)이 v38 값을 인용하며 *"transiently claims up to $3.1$\,GiB of host memory"*라 적는다.
확정표의 `hs_gen_rss_incr_max`는 **3099.0 MiB = 3.03 GiB**이며, 줄이 인쇄한 자릿수로 반올림하면
**3.0**이다.

```
main.tex:365: hs_gen_rss_incr_max = 3099.0 MiB 가 이 줄에 없다
    줄의 수치: 574, 1.8, 3.1, 18
    확정표를 줄의 자릿수로 반올림하면: 3 GiB, 3099 mib
```

같은 줄의 574 MiB(`hs_vision_vram_incr_max`)와 18×(`hs_gen_rss_headroom`)는 **일치한다.**
3.1은 십진 GB로 환산했거나(3099 MiB = 3.25 GB) 올림한 것으로 보이나 **확인하지 않았다.**
**본문을 3.0 GiB로 고치거나** 어느 단위인지 명시해야 한다 — 어느 쪽이든 사람 판단이다.
검사기에 MiB↔GiB 환산을 추가해 이 대조가 성립하게 했다(p99의 ms↔s와 같은 처리).

### 5.5 Q4 줄의 주석 정정은 도구가 못 한다

v38이 보고한 L742 주석 오류(`q4_b_lastV`의 294.2가 인쇄된 범위 293–315 안쪽이라 줄에 없다)는
**아직 정본에 남아 있다.** 목록은 정정된 id 집합을 담고 있으나 `apply_cv_annotations.py`는 이미
주석이 있는 줄을 건너뛴다. **정본에서 옛 주석을 지우고 목록을 다시 생성해야 한다** — 지우면 줄 해시가
바뀌므로 재생성이 필수다. 정정본:

