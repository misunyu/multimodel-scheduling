§1Models & devices

Defined in model_registry.py — the single source of truth. Every model runs on cpu gpu npu. Vision models report frames/sec; LLM/VLM report tokens/sec (headless, profiling + placement only).

Device constraint. qwen2_vl is restricted to gpu npu (CPU prefill ≈ 13 s is impractical). All other models may use any device. Both accelerators are shareable — multiple models can co-reside on one GPU or on the Mobilint MLA100.

§1bModel assets on disk

Vision models ship as two matching files per model. Generative models have no local binaries — the Mobilint runtime and transformers load them from HuggingFace. models/ is git-ignored (~900 MB).

models/├── onnx/ # CPU (and GPU) execution — ONNX Runtime│ ├── resnet50.onnx│ └── yolo11{n,s,m,l,x}.onnx├── mobilint/ # the compiled form for the Mobilint NPU│ ├── resnet50.mxq│ └── yolo11{n,s,m,l,x}.mxq└── pt/ # ultralytics sources used to export the ONNX

A vision model is deployable when both its .onnx and .mxq exist. If the .mxq is missing, the zoo fetches it from the Hub on first use and caches it under ~/.mblt_model_zoo/vision/aries/global8/; copy it into models/mobilint/ to pin it.

1profile_models.py

Measures each model on each device and writes the static profile (sample_profiling_data.json): load & inference time (vision), prefill + tokens/sec (LLM/VLM), and each model's baseline_rate (throughput on its slowest allowed device = the 1× input rate). Writes incrementally, so it can be run one model at a time.

$PYTHON_BIN profile_models.py --out xgboost_model/performance_data/sample_profiling_data/sample_profiling_data.json

2generate_schedules.py

Enumerates device placements for the working set (one detection model + resnet50 + llama1b + qwen2_vl) and expands each across the input-rate sweep. Per-view infps = rate_factor × baseline_rate. Writes the schedule YAML plus a <out>.meta.json sidecar (rate_factor, workload) used for the train/hold-out split and normalization.

3run_collection.py

Runs each combination in its own executor subprocess with a hard OS-level timeout and process-group kill, so a stuck worker can never stall the sweep. Each combination contributes one contention window (throughput, tokens/sec, deadline-miss rate); windows are tagged with rate_factor/workload from the meta sidecar and merged into one training JSON.

$PYTHON_BIN run_collection.py --schedule model_schedules.yaml --duration 8 \ --out xgboost_model/performance_data/train/performance_ratesweep.json
FlagDefaultDescription
--scheduleoptmodel_schedules.yamlSchedule YAML (its .meta.json sidecar is auto-loaded).
--outopt…/performance_collected.jsonMerged training-window output; written incrementally per combo.
--durationopt8Measured seconds per combination (Δ). Warmup is added on top.
--warmupopt5Warmup seconds before measurement (stats reset after warmup).
--bufferopt12Extra seconds before the per-combo timeout (load + cleanup headroom).

Per-combo wall-clock budget ≈ duration + warmup + buffer. Anything past it is SIGKILL'd and recorded as NO DATA, and the sweep advances.

4deploy_selector_xgb_suite.py train

Trains three independent XGBoost regressors — normalized throughput (y1), deadline-miss rate (y2), normalized token throughput (y3) — on the training rate levels only. Hyperparameters are chosen per target by 3-fold cross-validation over a small grid (MAE). Writes <prefix>_y{1,2,3}.json, a _features.json column order, and a _coverage.json record of the model sets, view counts, devices and rate levels the predictor actually saw.

$PYTHON_BIN xgboost_model/deploy_selector_xgb_suite.py train \ --perf_dir xgboost_model/performance_data/train \ --schedule_dir xgboost_model/schedules \ --static_json …/sample_profiling_data.json \ --model_out xgboost_model/artifacts/deploy_xgb

5deploy_selector_xgb_suite.py predict

Scores every combination in a schedule with the trained models and prints a ranking — no execution required. The score combines the three predictions; α and β are runtime-only weights (never part of training), so the throughput–stability trade-off is re-tunable without retraining.

S(x) = Tthroughput + β · Ttokens − α · missrate
$PYTHON_BIN xgboost_model/deploy_selector_xgb_suite.py predict \ --schedule_yaml model_schedules.yaml \ --static_json …/sample_profiling_data.json \ --model_in xgboost_model/artifacts/deploy_xgb --topk 5
FlagDefaultDescription
--schedule_yamlreq—Schedule whose combinations are scored and ranked.
--static_jsonreq—Static profile (same one used for training).
--model_inreq—Trained model prefix (expects _y1/_y2/_y3.json).
--alphaopt0.3Deadline-miss penalty weight (normalized units).
--betaopt0.5Token-throughput reward weight (normalized units).

§evaluate_model.py

Accuracy validation in three modes. All targets are normalized to [0,1]; reported per target: MAE, RMSE, R², MAPE. select reports paper-style per-workload Top-1 / Top-5 hit rate and the predicted pick's score relative to the oracle.

# 3-fold cross-validation on the training rates$PYTHON_BIN evaluate_model.py cv --perf_dir …/train --schedule_dir …/schedules --static_json …# unseen input-rate hold-out (3x)$PYTHON_BIN evaluate_model.py holdout --model_in …/deploy_xgb --test_perf …/train --schedule_dir … --static_json …# placement selection: Top-1 / Top-5 hit rate vs oracle$PYTHON_BIN evaluate_model.py select --model_in …/deploy_xgb --test_perf …/train --schedule_dir … --schedule_yaml model_schedules.yaml --static_json …

§XGBoost model

Three independent targets

  • y1 — normalized throughput: sum of vision FPS, normalized to [0,1] by Fmax within each (workload, rate) group: T = F / Fmax.
  • y2 — deadline-miss rate: mean of per-application miss rates (already in [0,1]).
  • y3 — normalized token throughput: sum of LLM/VLM tokens/sec, normalized like y1.

Separate regressors let α/β be re-tuned at runtime without retraining. Predictions are clipped to [0,1].

Features (no target leakage)

Static profile only — device one-hot (exec_cpu/gpu/npu), kind flags, selected-device inference / load / tokens, planned infps, device capacity and load factor — aggregated across views by sum / mean / max plus a view count. Measured per-window throughput is never a feature.

§Metrics

Deadline miss

A request misses if end-to-end latency > 1000/infps × 3 ms. Per view: offered = infps × Δ, on_time = completions within deadline, miss = (offered − on_time) / offered. Window value = mean over applications.

Placement ranking

Per (workload, rate) group, placements are ranked by predicted score. Top-1 / Top-5 hit rate = predicted best is (in the top-5 of) the measured oracle; the oracle-gap is the predicted pick's measured score ÷ the best measured score.

§Best-deploy finder (GUI)

The interactive front-end for the CPU + Mobilint NPU platform. It replaces the legacy CPU + Neubla flow and uses the trained deploy_cpu_npu predictor.

source runtime_env.sh && $PYTHON_BIN best_deploy_finder_executor.py
  1. The tree lists deployable model names (no extensions): vision models discovered from models/onnx ∩ models/mobilint, plus llama1b and qwen2_vl from the registry.
  2. Check the models to deploy. Predict Best Deployment enumerates every cpu/npu placement of exactly those models (2N, with qwen2_vl pinned to the NPU), scores each with the predictor, and writes predictions.csv.
  3. Load & Execute Best launches schedule_executor_main.py on the winning combination.

Per-view infps defaults to each model's baseline rate; override it per model with the input-rate dialog. The executor runs up to 8 views (MAX_VIEWS) and renders the first four; the rest execute headless and still contribute to throughput and deadline-miss statistics.

Out-of-distribution warning. Before predicting, the GUI compares the checked models with <prefix>_coverage.json. Every training working set was {one yolo11 variant, resnet50, llama1b, qwen2_vl} at rates 1–4×, so a vision-only or larger selection triggers a dialog naming the mismatch (unseen model, unseen view count, or an always-present model that was omitted). Prediction proceeds only if confirmed, and the ranking is then an extrapolation.

§Two-platform study

Reproduces the paper's per-platform evaluation: a CPU+GPU predictor and a CPU+NPU (MLA100) predictor, each trained and validated independently. One script runs collect → train → CV → hold-out → selection for both, appending to platform_study_report.txt.

./run_platform_study.sh # ~2.5 h; artifacts: deploy_cpu_gpu_*, deploy_cpu_npu_*

To run one platform manually, generate its schedule with --devices cpu gpu (or cpu npu), collect against it, then train with --model_out …/deploy_cpu_gpu.

Distributing work to the CPU is optimal on the NPU platform (the accelerator saturates) but never on the GPU platform — the RTX 5090 does not saturate.

§Concurrency study (CPU+GPU, N = 4…8)

Scales the number of concurrently running models from 4 to 8 by adding YOLO11 detectors smallest-first (n, s, m, l, x) on top of resnet50 + llama1b + qwen2_vl, to test whether GPU contention ever makes CPU placement optimal. A dedicated headless runner sidesteps the 4-view GUI.

$PYTHON_BIN generate_concurrency_schedules.py --out schedules_concurrency.yaml --cap 10$PYTHON_BIN run_concurrency_study.py --schedule schedules_concurrency.yaml --duration 8 \ --out xgboost_model/performance_data/concurrency_cpu_gpu/performance.json
FlagDefaultDescription
--n_min / --n_max4 / 8Concurrency range (models running at once).
--cap10Max placements sampled per N level (stratified by GPU-count).
--duration / --warmup8 / 5Measured seconds per combination, and warmup before it.

Finding. All-GPU throughput rises with N (239 → 329 FPS at N=8), so the GPU never saturates and all-GPU stays optimal at every N and every α. The paper's "distribute to CPU under contention" effect appears only on the weaker NPU.
