# 후보 순위 확인 — LLM-CPU 배치가 N_cand 이내인가

날짜: 2026-07-22 · 계산·검사 전용 (실험/코드변경/후보조작 없음) · 예측기·α=0.3·β=0.5 불변

## 질문
BoundGuard는 예측기 랭킹을 점수순으로 순회한다. Q3의 더 나은 대안(LLM=CPU)이 탐색 예산 $N_{cand}$
안에 있으면 자연히 도달하고, 밖이면 도달 못 한다. 이 순위를 **관찰만** 한다(끼워넣기 금지).

## §1. 후보 공간에 LLM-CPU 조합이 존재하는가 — **존재**
- `schedule_generator_logic._build_schedule_cpu_gpu`: "each model → cpu or gpu (**2^N combinations**)".
  모든 모델의 device를 변주하므로 `llama1b=cpu`인 조합이 후보 공간에 **당연히 포함**. (확인: 16조합 전수에
  LLM=CPU 8개 존재.)

## §2. 실제 N_cand 값·출처, BoundGuard 후보 소비 방식
- **$N_{cand}=5$** — 하드코딩 상수가 아니라 하네스 관례: `scripts/q13_failure_persistence.py`
  - 주석 L17: `BoundGuard : stable, burst, cand_1..cand_5 (mode 1)`
  - L188: `top5 = df.head(5)` — 예측기 `predict_best_combination(alpha=0.3)`의 **점수순 상위 5개**를
    cand_1..cand_5로 공급, 각 후보를 T_v(3s) validate, **검증 실패 시 다음 후보로 하강**, cand_5에서 tail.
  - (q13의 `VIEWS`는 legacy vision-only 세트 resnet50/resnext50/vgg19/yolov4 + 구 gpu 아티팩트 → 신규
    mixed Q3 세트 아님. 하지만 **후보 소비 패턴(head(5), 점수순)**은 동일 적용.)

## §3. 전체 랭킹 (Q3 워킹셋 = llama1b + yolo11s/resnet50/mobilenet_v2, §4 검증과 동일)
cpu_gpu 예측기, α=0.3, β=0.5. 배치 표기 `[llama|yolo|res|mob]`, G=gpu C=cpu.

| # | llama\|yolo\|res\|mob | LLM | y1 | y2 | y3 | βy3 | −αy2 | S |
|--:|---|---|--:|--:|--:|--:|--:|--:|
| 1 | GGGG | gpu | 0.986 | 0.000 | 0.974 | 0.487 | −0.000 | **1.473** |
| 2 | GGGC | gpu | 0.762 | 0.317 | 0.583 | 0.291 | −0.095 | 0.958 |
| 3 | GGCG | gpu | 0.673 | 0.337 | 0.586 | 0.293 | −0.101 | 0.864 |
| 4 | GCGG | gpu | 0.667 | 0.576 | 0.581 | 0.291 | −0.173 | 0.785 |
| **5** | **CGGG** | **cpu** | 0.806 | 0.717 | 0.346 | 0.173 | −0.215 | **0.764** ← LLM=CPU 최고 |
| 6 | GCGC | gpu | 0.418 | 0.616 | 0.522 | 0.261 | −0.185 | 0.494 |
| 7 | GGCC | gpu | 0.416 | 0.604 | 0.515 | 0.257 | −0.181 | 0.493 |
| … | (8–16) | | | | | | | 0.420 … −0.053 |

- **LLM=CPU 최고 순위 = 정확히 5위 / 16** (CGGG: llama1b=cpu, vision 전부 gpu).
- 5위와 6위 사이 간격 큼(0.764 → 0.494) → CGGG는 **견고하게 5위**(6위로 안 밀림), 그러나 **정확히 경계**.

## §4. 순위 구조 해석 (§4 가설 완벽 확인)
- **2~4위가 전부 "LLM은 GPU 유지, vision 하나만 CPU로"**(GGGC/GGCG/GCGG). y3(생성 토큰)를 GPU에서
  보존하므로 βy3≈0.29를 유지 → LLM-CPU보다 상위. → **y3 보상이 정답(LLM-CPU)을 정확히 5위로 밀어냄.**
- LLM-CPU(CGGG) 강등 원인 항별 분해:
  - **βy3 손실이 지배적**: LLM을 CPU로 빼면 y3 0.974→0.346, βy3 0.487→0.173 (약 −0.12 vs LLM-GPU 후보).
  - **y2 반전이 보조**: 예측기가 LLM-CPU의 y2를 0.717로 **더 높게(=miss 많다고)** 예측 → −αy2가 rank-4
    대비 약 −0.04 추가 불리. (실측은 반대: LLM-CPU miss 0.472 < LLM-GPU 1.000 — 예측기가 GPU 경합 미모델링.)
- **워킹셋 크기 민감도** (계산, 참고): vision 3개=5위, 4개=5위, **5개=6위(예산 밖)**. y3-보상이 만드는
  "LLM-GPU 유지 + vision 일부 CPU" 조합이 워킹셋이 커질수록 늘어 정답을 예산 밖으로 밀어냄.

## 판정 매트릭스 (사전 고정)
| LLM-CPU 최고 순위 | 위치 |
|---|---|
| N_cand=5 이내 | (기술적으로 해당: 5위=cand_5) |
| N_cand=5 밖 | — |
| **정확히 N_cand번째** | ← **여기 (경계 사례)** |

### 판정: **경계 사례 → 판정 불가 (근거 명시)**
- LLM-CPU는 **정확히 5위 = BoundGuard의 마지막 후보(cand_5)**. 기술적으로는 예산 이내라 순회하면 도달하나,
  **cand_1~4가 모두 LLM=GPU 유지 조합**(경합 하에서 vision QoS 회복 안 됨) → BoundGuard는 **가장 마지막
  후보에서만, 제로 마진으로** 회복. 어떤 여유도 없음.
- 게다가 경계는 **워킹셋 크기 의존**: vision 5개면 6위로 밀려 **도달 불가**. 현 Q3 세트(vision 3)에서만
  간신히 5위.
- 따라서 "교과서적 Q3(여유롭게 도달)"도 "명백한 도달 불가"도 아님 → **매트릭스 규정대로 판정 불가.**

### 함의 (사람 판단)
- **후보 조작 금지 준수**: LLM-CPU를 인위 삽입하지 않음 — 관찰 결과 그대로 보고.
- Q3 실험을 현 세트로 진행하면 BoundGuard는 cand_5에서만 회복(제로 마진) → 교과서적 시연으로는 취약.
- 대안(사람 판단): (a) $N_{cand}$ 근거 재검토(정답이 예산 가장자리에 놓이는 구조), (b) QoS 기준 순위
  재정렬 검토(y3-보상이 vision QoS 배치를 밀어내는 목적함수 문제), (c) 이 경계·강등 구조 자체를
  "ML 배치의 구조적 위험"으로 논문에 서술. — 어느 것도 후보 목록 조작은 아님.
