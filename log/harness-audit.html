A먼저 판단이 필요한 발견

계획된 실험 순서를 그대로 진행하면 막히거나, 결과를 합칠 수 없게 되는 항목.

정정됨A1

“venv 드리프트”는 파일시스템 증거와 맞지 않는다 — §10에서 정정

최초 보고는 env_snapshots/README.md를 그대로 받아 “논문 시점 torch 2.8+cu128 → 현재 2.12+cu130 드리프트”라고 적었다. 이후 환경 조사 결과, .venv의 torch 2.12.0은 2026-05-27 14:56 설치 이후 한 번도 바뀌지 않았고 6/9 이후 ML 패키지 변경이 하나도 없다. 앵커 미재현(24.3 % → 59 %)의 원인은 패키지 버전이 아니라 재측정 스크립트 쪽 차이로 보인다. 증거와 두 개의 구체적 원인 후보는 §10에 있다.

차단A2

TensorRT가 설치돼 있지 않다

.venv에 tensorrt, pycuda 모두 없고 trtexec도 PATH에 없다. 세션 2 단계 1은 설치부터 시작해야 하며, torch 2.12+cu130 환경과 충돌하지 않는 버전 선택이 선행 작업이다.

주의A3

NPU 재컴파일 경로가 현재 깨져 있다 — 단 재컴파일은 아마 불필요

qbcompiler.mmc import가 undefined symbol: _ZN3c104impl12PyObjectSlotD1Ev로 실패한다(torch ABI 불일치). 다행히 세션 3에 필요한 ResNet50 NPU 바이너리는 이미 존재한다 (models/mobilint_backup/resnet50.mxq, HF 캐시 resnet50_IMAGENET1K_V2.mxq). 새 mxq가 필요해지는 순간 막힌다.

확인 요청A4

vendor calibration set은 repo에 없다

foreground yolo11s의 mxq는 Mobilint가 배포한 사전 컴파일 바이너리이고, 그 calibration 데이터는 미상이다 — qbc_compile_check.py:4가 “vendor calib unknown”이라고 명시한다. repo에 있는 것은 로컬 컴파일용 qbc_calib200(Argoverse-HD val 균등 200장)과 qbc_calib200_train뿐이다. 세션 2의 “NPU와 동일한 calibration set”은 원리적으로 맞출 수 없다. TensorRT INT8 calibration에 무엇을 쓸지 결정이 필요하다.

주의A5

기존 run에는 git commit hash도 라이브러리 버전도 기록돼 있지 않다

manifest_rev30.json은 {done: {key: {ts}}}뿐이고, raw CSV의 메타데이터는 run_id / t_start / t_end / period_ms / fps / detector / dataset / timestamp가 전부다. 세션 4 단계 2의 “metadata의 git commit hash로 대조”는 기존 데이터에 대해서는 수행 불가이며, 신규 run부터 기록을 시작해야 한다.

블록 구조는 이미 존재한다 — 다만 순서가 고정이다

rev30의 실행 루프는 for k → for rep → for r in 0..4이므로, 하나의 (k, rep)가 동일한 4개 log·동일한 co-tenant 설정에서 5개 placement를 연속 측정하는 paired block이다. 세션 4가 요구하는 “블록 안에서 먼저 차이를 만든다”는 기존 데이터로 그대로 가능하다. 단 순서는 항상 GGGG → GGNG → GGNN → GNNN → NNNN으로 무작위화돼 있지 않다 — All-GPU가 늘 먼저, All-NPU가 늘 마지막이다. 신규 측정에서 balanced randomized order를 쓰면 이 점이 기존 데이터와 다른 조건이 된다는 것도 함께 기록해야 한다.

2co-tenant의 실제 설정값

모델별 batch·shape·요청 방식·k·프로세스 구조·동기화·host-side 작업

핵심

co-tenant는 전부 foreground와 동일 프로세스 안의 thread이고, rate limit 없는 back-to-back 루프이며, 입력 텐서는 프로세스 시작 시 1회 만들어 재사용한다. 따라서 co-tenant의 host-side 전처리·후처리는 사실상 0이다(Python 루프와 런타임 launch 오버헤드만). 세션 3에서 “host 작업을 동일하게 유지”한다는 것은 곧 “양쪽 모두 host 작업이 없도록 유지”를 뜻한다.

  • 동시 instance 수 k — ResNet50만 sweep된다: k ∈ {0,1,2,3,4,6,8} (rev30 KS, rev22 RESNET_COUNTS). L2LM·L3VLM은 각 모델 1 인스턴스 고정.
  • 레벨 정의 — L1_light = resnet×1, L1_heavy = resnet×3, L2_lm = resnet + tinyllama, L3_vlm = resnet + qwen2vl. L3_vlm에 tinyllama는 들어 있지 않다 (누적이 아니라 교체).
  • CUDA stream — 명시적 배치 없음. ORT 세션은 각자 기본 스트림, torch는 default stream. 확인된 제어 코드 없음.
  • 동기화 — 셀마다 start_bg_custom() → sleep(0.3) → foreground thread start, 셀 종료 시 stop_background(). 모델 로드와 warm-up은 프로세스 시작 시 1회 (preload_background_models), 순서 강제: ORT 세션들 먼저, torch CUDA 모델 마지막.
  • 실제로 도는가 — 돈다. 로드만 하는 코드 경로는 없다.
  • co-tenant throughput/latency 로깅 — 없음 repo 전체에서 co-tenant의 반복 횟수·지연을 기록하는 코드가 없다. 세션 2의 신규 항목이 맞다.

Qwen2-VL 입력의 비주얼 토큰 수는 로그에 없다. preprocessor_config.json의 max_pixels 12,845,056보다 이미지(6.03 M px)가 작아 축소가 걸리지 않으므로 patch 14 · merge 2 기준 약 1.9 k 토큰으로 계산되지만, 이것은 파생 추정이며 측정값이 아니다. 정확한 값이 필요하면 런타임에서 찍어야 한다.

3frame handling

deadline을 놓친 뒤 queue인가, drop인가, 최신 프레임 교체인가?

확인

queue 없음. 항상 “현재 가상 시각의 최신 프레임”으로 교체하고 사이 프레임은 버린다. 루프는 fidx = floor(t_elapsed · FPS)로 다음 입력을 고르고, 추론 후 t_elapsed += rt로 시계를 전진시킨다. 같은 fidx가 다시 나오면 강제로 +1 한다.

7“N=4, co-tenant 없음” 조건의 존재

sweep의 좌측 끝은 co-tenant 0인가, 이미 co-tenant가 있는 상태인가?

확인

진짜 co-tenant 0이다. sweep의 좌측 끝은 k = 0이고, k=0은 background thread를 하나도 띄우지 않는다(BG_VARIANTS["R30K0"] = [], start_bg_custom이 빈 리스트면 즉시 반환). N=4 기준 3 reps ×5 placement가 남아 있고, GPU 프레임스킵 0.0 %, All-GPU worst 0.1149, All-NPU worst 0.0836이다. cpuload의 baseline(L0) 역시 co-tenant 없는 All-NPU N=4 3 reps다.

8부수적으로 확인된 불일치

계획을 바꾸지는 않지만 보고서·원고에 영향이 있는 항목.

“14 s evaluation window”는 코드 상수가 아니다

  • 프레임 절단 코드가 repo 어디에도 없다. 창 길이는 선택된 log 길이에서 파생된다.
  • PANEL4 = sid 2·22·3·21 = 469/475/475/469 프레임 = 15.6–15.8 s. 여기서 warm-up 30 프레임(1 s)을 빼면 14.6–14.8 s → 논문의 “14 s”.
  • 단일 스트림 24 log 비교(Table 1)의 창은 13.7 s ~ 29 s로 제각각이다. 논문 문장 (main_vision.tex:165)은 이 조건에는 정확하지 않다.
  • 세션 2·3에서 “14 s window”를 재현하려면 같은 sid 패널을 쓰는 것이 유일한 방법이다.

NPU infer_mode 표기 불일치

  • paper/results_data/MANIFEST.md는 infer_mode global8이라고 적었지만, 실제 실행 경로는 DETECTORS["multistream_mode"] = "single"이다 (phase_rev6_sweep.py:57, phase_rev30_clean.py:60).
  • mxq 자체는 동일하다: b2441f9d… (HF blob = models/mobilint_backup/yolo11s.mxq, mxq_provenance.csv로 대조 확인).

end-to-end latency 정의 (Table 1의 8.3 / 10.0 ms)

  • infer_ms = predict() 또는 npu_infer() 호출 전체 시간 — 이미지 읽기 + 전처리 + 추론 + decode/NMS를 모두 포함하며, warm-up 이후 구간의 평균이다.
  • 세션 2에서 GPU-INT8 경로를 만들 때 이 경계를 그대로 유지해야 한다.

NPU 코어 구조와 instance quota

  • MLA100(Aries) = 2 cluster × 4 core = 8 core. single 모드가 코어당 독립 인스턴스로 최대 8 스트림 (docs/mla100_npu_guide.html §7).
  • 다만 mblt wrapper는 single 모드에서 모든 인스턴스에 8개 core id를 전부 넘긴다 (wrapper.py:255–267). 실제 코어 배정은 qbruntime 내부이며 repo 문서로는 확인 불가.
  • 따라서 “foreground N=4 + co-tenant k ≤ 4”라는 세션 3의 가정은 합리적이지만 미확인이다. 벤더 SDK 문서 또는 실측이 필요하다.
  • 추가 위험: HF의 ResNet50 mxq는 aries/ 아래 mode 하위폴더 없이 단일 파일이고 ResNet50 클래스 기본 infer_mode는 global8(=8코어 점유)이다. single foreground와 global8 co-tenant의 공존 가능 여부가 세션 3 단계 0의 실제 관문이다.

9세션 2·3·4에 대한 영향

이번 조사 결과로 각 세션에서 바뀌어야 하는 것.

세션 2 — matched-precision control

  • TensorRT 설치가 선행 작업 (A2).
  • calibration set을 NPU와 “동일하게” 맞추는 것은 불가능하다 (A4). 결정 필요: qbc_calib200(Argoverse-HD val 200장)을 쓸 것인가.
  • 비교 대상인 All-NPU under L3VLM의 per-stream 원자료가 기존에 없으므로, 계획대로 블록 안에서 새로 측정하는 것이 맞다 — 기존 값 재활용 여지가 없다.
  • NPU 경로의 post-processing 위치는 이미 host CPU · 4 threads · conf 0.25 / IoU 0.45 / max_det 300이다. TensorRT 쪽에서 이 조건을 맞추면 된다.

세션 3 — contention-location control

  • ResNet50 NPU 바이너리는 이미 있다 → 재컴파일 불필요할 가능성이 높다 (A3).
  • 단계 0의 실제 관문은 “ResNet50 지원 여부”가 아니라 infer_mode 공존과 코어 배정이다 (§8).
  • “same workload” 정의는 §2 표 그대로: batch 1, (1,3,224,224), back-to-back, host 작업 없음, k는 GPU-side와 동일한 값.
  • gate로 제시된 NPU DM 24 %는 State A(rev30 k=1 = 24.3 %) 수치다. 현재 환경에서 같은 설정의 GPU-side는 59 %로 측정된 바 있다 (A1). gate 기준값을 절대값으로 쓸지, 현재 환경에서 재측정한 GPU-localized 하단으로 쓸지 결정이 필요하다.

세션 4 — 통계 보강

  • 단계 1(기존 로그 재집계)은 지금 바로 가능하다: rev30의 per-stream·per-repeat 원자료로 k별 d(C)와 paired t-CI를 계산할 수 있다 (n = 3–10).
  • 단계 2(부족분만 추가)는 §10 이후 다시 가능해 보인다. .venv의 실험 관련 패키지가 rev30 이후 하나도 바뀌지 않았으므로, shim 없이 · 문서화된 초기화 순서로 돌리면 기존 run과 같은 환경일 개연성이 높다. 다만 합치기 전에 ResNet k=1 셀 3회를 재측정해 24.3 %가 재현되는지 먼저 확인해야 한다. 재현되면 부족분만 추가, 재현되지 않으면 대표 3개 지점을 n=10 전부 새로 측정.
  • crossover bracket은 기존 데이터만으로도 k=2와 k=3 사이로 이미 좁혀져 있다.

rev30이 어느 환경에서 돌았는가

  • 직접 증거 — phase_rev30_clean.py:204가 util 샘플러를 <repo>/.venv/bin/python으로 하드코딩해 띄운다.
  • 배제 증거 — .venv_qbc에는 ultralytics도 qbruntime도 없어 실험 자체가 불가능하다.
  • 패키지 변경 이력 — .venv에서 6/9(rev20·rev22) 이후 설치된 것은 xlsxwriter·lxml·python-pptx(6/11), reportlab·pypdf(6/15), py-spy(7/3), colorama·onnxslim(7/8)뿐이다. torch·ORT·CUDA·ultralytics는 하나도 바뀌지 않았다.
  • 별도 env 기록 — poetry.lock·conda yaml 없음. Dockerfile은 CPU-only 이미지라 이 측정과 무관. rev30의 full.log에도 셸 히스토리에도 버전 출력이 없다.

ORT-CUDA는 rev30 시점에 정상이었다

All-NPU 셀에서는 GPU 부하가 co-tenant에서만 나온다. rev30의 NVML 기록은 k=0에서 0 %, k=1에서 76.9 %(power 65 W → 235 W, GPU 메모리 3.0 GB → 7.7 GB@k=8)로 올라간다. 즉 ResNet50 co-tenant는 6/28 당시 GPU에서 돌고 있었다 — “paper-era에도 ORT가 CPU fallback이었다”는 서술은 데이터와 맞지 않는다.

그렇다면 24 % → 59 %는 왜 났나 — 확인된 두 개의 후보

후보 1 · a2 재측정 스크립트가 문서화된 초기화 순서를 어겼다

  • _step_d_common.py:286–290은 “ORT CUDA 세션을 torch CUDA 모델보다 먼저 만들어야 하며, 아니면 ORT 1.20이 CUDA EP 초기화에 실패한다”고 명시한다.
  • rev30·rev22·rev20은 preload_background_models()를 먼저 호출한다.
  • 반면 a2_anchor_check.py는 FGModelGPUGeneric(:78)과 NPU 엔진(:79)을 먼저 만들고 preload_background_models("L2")를 나중에(:81) 호출한다. a2_repro_check.py도 동일(:85–88). 순서가 뒤집혀 있다.

후보 2 · ORT shim이 torch의 cuDNN까지 바꿔치기한다

  • vendor_ort_cu12/README.md는 “소네임이 .so.12 vs .so.13으로 달라 공존한다”고 적었다. cuBLAS·cudart는 맞지만 cuDNN은 양쪽 다 libcudnn*.so.9로 동일하다 (shim 8개 파일, torch 번들 8개 파일 이름이 완전히 같음).
  • ort_env.sh는 이 디렉터리를 LD_LIBRARY_PATH 맨 앞에 붙인다 → shim을 source한 프로세스에서는 torch도 CUDA-12용 cuDNN 9.12를 로드하게 된다.
  • a2 앵커 재측정은 shim을 source한 상태에서 수행됐다(a2_anchor_check.py:1). 즉 GPU foreground가 rev30 때와 다른 cuDNN으로 돌았다.

두 후보 모두 패키지 버전 변화 없이 앵커 차이를 만들 수 있다. 아래 §11이 이를 실측으로 확인한다.

판정과 다음 단계

  • 기각된 것 — “ORT-CUDA가 shim 없이는 CPU로 떨어진다”, “앵커가 59 %로 드리프트했다”. 두 실행 모두에서 재현되지 않았고, 재부팅 후에도 마찬가지다.
  • 설명된 것 — cold 실행의 어긋남은 warm-up 부재 때문이다. k=0 접두부를 넣자 GGGG DM 평균이 29.73 → 24.19(rev30 24.30), paired d가 +0.00782 → +0.01478(rev30 +0.01497)로 돌아왔다.
  • 남은 것 — 접두부 실행의 rep 간 산포가 rev30보다 크다(DM sd 4.58 vs 2.32, n=3이라 추정 자체가 불안정). n=3으로는 두 분포의 일치를 확인할 검정력이 없다.
  • 결정(사전 규칙대로) — 기존 rev30 reps와 신규 reps를 합치지 않는다. 세션 4의 대표점은 신규 환경에서 n=10 전부 새로 측정한다. 비용은 크지 않다: k=1 블록 하나가 68초이므로 대표점 3개 × 10 rep ≈ 35분이다.
  • 다음 측정 전에 고정할 기준 — 범위 포함(range containment) 대신 검정력 있는 형태로. 예: 신규 n=10의 d와 rev30 n=10의 d에 대한 Welch 이표본 검정, 또는 사전에 정한 등가 한계 (예: |Δd| < 0.005)에 대한 TOST. 어느 쪽이든 데이터를 보기 전에 정한다.
